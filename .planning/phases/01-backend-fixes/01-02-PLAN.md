<objective>
BACK-17 core, per D-01 and D-02 (deploy wave 1, D-10): make the push routing fields platform-neutral and add a per-recipient `target_role`.

- `sendPushToUser` sends `category` and `sub_category` in the FCM data map for every token (iOS, Android, legacy rows with no platform), adds `target_role` when known, keeps the Android-only `android.notification` block Android-only.
- A new `in_app_meta` option lets callers store data on the in-app notifications row without putting it in the FCM payload (used by BACK-02 in plan 01-06 to keep the free-text decline note out of FCM data).
- Every booking-lifecycle push in `events.js` passes the recipient's role.

The remaining call sites are wired in plan 01-03 (chat, review, payment webhook, reminders) and plan 01-04 (no-show, review nudge, long-lead charge, and the two account-level pushes, which derive the role with `targetRoleForAccount`). D-02 says every call site must supply or derive `target_role`, and no exemption for account pushes has been approved, so none is left without one.

User decision (2026-11-07, Open Q1/F1): accepted. Build 6's `PushEvent` reads `category` first, so taps on confirmed, declined, cancelled, reminder, no-show, nudge and payment-action pushes start navigating on build 6 as soon as wave 1 deploys. The wave-1 smoke checklist (plan 01-10) covers it.

<assumptions>
- [PROBE-UNRESOLVED] BACK-17 (edge probe: unclassified, left unresolved). Assumed edges: an empty or missing category is sent as an empty string (existing `String(category || '')` coercion) and Phase 2 routes empty or unknown categories to the notifications list; a recipient who is neither the booking's client nor its expert gets no target_role key (a defensive branch: no call site passes such a recipient).
- Account-level pushes (password change and account deletion request in account.controller.js) carry the recipient's primary role from `targetRoleForAccount(req.user.roles)`, wired in plan 01-04. Why primary role: it mirrors the backend's own scalar `role` ('expert' once an account holds the expert role, the same rule `authenticate.js` uses to build `roles`); `account/*` routes to the security screen, which both shells on both clients have, so either value is routable; a stale JWT (RESEARCH Pitfall 1) can only yield 'client', a role every account holds.
- Why the helpers live in `src/utils/pushTargetRole.js` and not only in push.js: every test suite of a push sender (chats, reviews, webhooks, the four crons, account, userPassword, events) mocks `../src/services/push` with a factory that defines only `sendPushToUser`, so a helper imported from push.js would be undefined in those suites. Callers import from the util; push.js re-exports it for push.test.js and for one obvious home.
- connectWebhooks.controller.js pushes pass `is_expert_only: true`, so they get target_role 'expert' from the default without a call-site edit.
</assumptions>

<objective>
BACK-18 per D-16 (deploy wave 2, D-10): unread counts are maintained by the server. Increment on send, reset on `message.read`.

Claude's discretion and RESEARCH recommendation: no atomic-increment RPC (that would need a migration). The counter is recomputed from `messages.status` ("messages from the other party not yet read") at the three moments it can change, which is race-tolerant and self-healing:
1. on send, for the recipient (inside `postUserMessage` from plan 01-09, so the accept message counts too);
2. on `message.read`, for the reader (the handler is extracted from a socket closure into an exported, testable function);
3. Open Q6 default adopted: on `GET /chats/:id/messages` page 1, for the caller. This is a recompute, not a forced zero: messages are only marked read by `message.read`, which Android emits for visible messages and re-sends after reconnect (ChatThreadViewModel.emitPendingReads), so the badge clears once the read reaches the server. Forcing zero would drift from message status and is a read-receipt change that belongs to Phase 7.

RESEARCH F5: Android shows `maxOf(server, local)`, so a reliable reset path matters; docs/SOCKET-CONTRACT.md section 6 ("unread_count is not maintained") must be rewritten. iOS build 6 ignores the field.

Canon note: a reader resetting only their own counter is standard participant access control (IDOR), covered by the threat model and /gsd-secure-phase.

To avoid a require cycle (chatMessages.js already requires socket.js), the recount lives in a new `src/services/unreadCounts.js` that depends only on Supabase.
</objective>

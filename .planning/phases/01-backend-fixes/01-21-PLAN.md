BACK-08 ("A client account is never shown the Stripe tax-ID prompt"), delivered from a code trace rather than the RESEARCH A7 hypothesis (2026-11-07 revision). This plan also locks the full BACK-13 route classification with a table test (moved here from plan 01-20 to keep plan sizes down).

**Seam trace (verified this revision; evidence with file:line is in RESEARCH "BACK-08 seam trace").** A tax-ID prompt can reach a user in exactly three ways, and each one runs through a gated `/expert/*` route:
1. The in-app Tax & Payout Info form (TIN field, copy "Required by Stripe to process your payouts"). On iOS it is reached from the unconditional row in `ExpertProfileHomeScreen.swift:120`. On Android it is reached from `HomeExpertScreen.kt:316` and `SettingsEntries.kt:79`. Both are expert shell only. It loads with `GET /expert/tax-profile` and saves with `POST /expert/tax-profile`.
2. Stripe-hosted Express onboarding, which asks for the SIN. It opens from expert Payouts via `POST /expert/connect/onboard`, the only code that creates a Connect account (`connect.controller.js:66`).
3. Stripe's own follow-up requests for an existing Connect account, and the `KYC_ACTION_REQUIRED` push (`connectWebhooks.controller.js:156`). Both need a `payout_accounts` row, which only (2) creates.
Nothing else collects a tax ID: there is no `tax_id_collection`, customer tax ID or PaymentSheet billing-detail setting in the backend or in either client. Today `ensureExpert` promotes anyone who calls those routes, and that is how a client account could reach them. This holds whatever happened to Android test account B.

**After plan 01-20, for a client-only account:**
- Android: the mode switch calls `GET /expert/profile` (no promotion) and lands on the setup hub; "Not now" returns to client home (`AppViewModel.kt:223`). The expert shell, and with it surfaces 1 and 2, cannot be reached until setup promotes the account. Closed.
- Stripe side (surfaces 2 and 3), any client: `POST /expert/connect/onboard` gets 403 at the gate. Task 1 adds a refusal inside `postOnboard`, so no Connect account can be created for a non-expert even if a later route edit drops the gate. Closed.
- Build 6 iOS: `ModeSwitchView` opens the expert home for any role (inventory S7, fixed by iOS Phase 5 SIGN-06), and the Tax & Payout Info row is unconditional. So a client-only user who opens Expert, then Profile, then Tax & Payout Info triggers `GET /expert/tax-profile`. Under D-08 as written (reads return their empty response) that is a 200 with `tin_on_file:false`, and build 6 renders the TIN form; saving is refused with 403. This is the one surface left. The backend can close it only by making that one GET return 403, which departs from D-08's GET rule. Task 2 asks the user to decide (blocking-human) and Task 3 implements the choice.

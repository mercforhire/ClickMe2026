**Stripe facts this plan relies on** (docs.stripe.com, read 2026-11-08):
- The PaymentIntent status list has no refund state (requires_payment_method, requires_confirmation, requires_action, processing, requires_capture, canceled, succeeded), so a refunded PaymentIntent is expected to read `succeeded` and its status cannot show a refund already made. `Charge.amount_refunded` holds the refunded amount; `Charge.amount_captured` can be below `Charge.amount` after a partial capture.
- For `refunds.create` Stripe saves the first result for an idempotency key once the endpoint starts executing, including errors, and replays it. A key can be pruned once it is at least 24 hours old. So after a sweep's own `createRefund` fails, later runs may replay that error until the key is pruned. The sweep keeps the key anyway, because double-refund protection matters more. The handler's first `createRefund` has no key, so its failure blocks nothing.

**Why reading the PaymentIntent is not enough:** the 01-19 note says "Succeeded: refund the saved amount". Read alone, that repeats a refund that went through but whose response was lost, and a manual partial refund. So the succeeded branch also reads the Charge.

|----------|-------------|
| cron process to live Stripe | An unattended job moves real money on any row that has the flag |
| bookings row to cron | The saved amount and flag decide a refund, so they must never come from a request |
| backend to client apps | Booking detail tells the client whether money came back |

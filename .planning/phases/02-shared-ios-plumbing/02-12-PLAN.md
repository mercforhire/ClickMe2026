<objective>
PUSH-04: after logout this device stops receiving the old account's pushes. Plus the phase close-out: the Phase 2 device checklist and the D-01 record of Q3 in REQUIREMENTS.md and ROADMAP.md.

Purpose: `logout()` starts the unregister in a Task and then clears the bearer on the next line, so the unregister's own signed-in guard always returns early and the DELETE is never sent (research Pattern 9). A shared device keeps getting the previous user's pushes.

Output: `PushTokenCleanup` (injected closures, tested), `UserManager` logout paths rebuilt on it, the device checklist, and the docs sync.

Backend: no change. `POST /notifications/tokens` deletes the caller's rows and evicts the same token from other accounts, and the push sender deletes rows whose FCM token comes back unregistered (research, `notifications.controller.js`, `push.js`). That is why the saved retry covers deleteToken only and never the server DELETE (D-18).
</objective>

- Order: unregister (bounded, bearer still set), then clear the session, then deleteToken (bounded). deleteToken needs no credential, so the user is not kept on the screen for it. The marker is saved before the session is cleared and removed only after both steps succeeded, so a kill mid-logout still leaves a retry (deleteToken only, D-18).
- The retry is deleteToken only, because the DELETE needs the old bearer (D-18, which amends D-06 and answers its research flag with research Pattern 9). Residual window, accepted by the user under D-17: if the DELETE and every deleteToken attempt fail while offline, the old account's pushes can arrive until the next launch or login retries the cleanup (or until FCM reports the token dead on the next push, or another login on this device evicts the row). The retry stays at launch and login only; no foreground retry of the cleanup is added (D-17). The `scenePhase` hook plan 02-10 adds to the home shells re-plans a queued push tap; it does not touch the cleanup.
- Clearing the session is idempotent; a 401 during the DELETE can trigger the refresh path's involuntary logout first, and the later clear is a no-op.
- `PushTokenCleanup` keeps the target's MainActor default; its closures are main-actor.
- After deleteToken (research A2), FCM is expected to return UNREGISTERED for the old token, so the backend reaper deletes the row on the next push. Verified only by the device check.
- Android: no change needed; Android ships this flow (`FcmPushTokenRegistrar.kt`).

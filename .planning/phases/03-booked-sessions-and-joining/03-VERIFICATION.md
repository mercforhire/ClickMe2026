### Review Warnings Weighed Against the Goal

| ID | Verdict | Why |

| WR-01 stale card after a failed post-accept refetch | Non-blocking warning, fix recommended | Confirmed in code. `accept()` shows the toast, then awaits `refetch`. `refresh()` swallows a failed GET by design, and a test pins that. The card stays. The backend answers a repeat accept with an idempotent 200, so the money is safe. A repeat decline also returns an idempotent 200 ("declined") for a booking that is already confirmed, so the user would see "Reschedule declined" on a booking that moved. This needs a successful POST, then a failed GET, then a contradicting tap. The happy path and the single-flight guard are tested, so no must-have fails. The fix is cheap: clear the proposal locally after a 2xx. It bears on "accurate status", so do it before release. |
| WR-02 toast promises a refund the server did not issue | Non-blocking warning, product decision | Confirmed. The case is chosen with the device clock, and a server `refund_amount` of 0 under `.chargedRefundable` reads "refund is being processed". That wording is deliberate: the backend also returns 0 while a refund is retried, and a test pins it. It is wrong only with a skewed phone clock or the idempotent already-cancelled 200. The plan's prohibition (never say "no refund applies" except for a charge inside 24 hours) is respected. Neutral wording would remove the edge. |
| WR-03 list price instead of `amount_paid` | Accepted limitation, not a gap | The user dismissed this on 2026-11-10 (UI-SPEC U2 and U3, RESEARCH).

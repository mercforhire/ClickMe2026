<objective>
Gap G-04-3 of 04-UAT.md (UAT test 3, EXPL-07, severity blocker). On a real iPhone on 2026-11-12, pull to refresh on the client Explore screen loaded nothing. The initial load and the airplane-mode error state worked. Diagnosis, from code and not yet confirmed under a debugger: `load()` sets all three sections to `.loading` when a refresh starts, so the ScrollView that owns `.refreshable` swaps its loaded sections for skeletons. SwiftUI cancels the refresh task when that content re-renders, `getClientHome` throws `URLError.cancelled`, and the cancellation branch moves every loading section back to `.idle` with no fetch in flight. `.idle` draws the same skeleton as `.loading`, so Explore stays on skeletons.

This plan:
1. Runs every Explore fetch in an unstructured `Task` that `load()` and `reload()` await, so SwiftUI cancelling the refresh task (or the `.task` task) never reaches URLSession.
2. Keeps sections that already show content on screen during a refresh, so the refresh no longer swaps content under the refresh control.
3. Makes a cancelled fetch settle each section from what it showed before: its content, its failure with Retry, or the generic failure for a first load. A cancelled fetch never leaves a section at idle.
4. Leaves the EXPL-07 behaviors and the category-change skeletons unchanged.
5. Adds nine Swift Testing rows through the view model's API seam and `MockURLProtocol`.
6. Adds the device re-test to the checklist.

Purpose: UAT test 3 can pass, which means Explore loads every time, including on a pull to refresh and on a refresh after airplane mode is turned off (G-04-3 truth). It also clears the path for EXPL-07's device check.

Output: changes to ExploreClientViewModel.swift, one comment in ExploreClientView.swift, nine rows and three helpers in ClientHomeFeedTests.swift, a lock around `MockURLProtocol.recordedRequests`, and step 4 of item 1 in 04-DEVICE-UAT-CHECKLIST.md.

It has the same semantics as the usual `.refreshable { await Task { … }.value }` idiom: an unstructured task is not a child of the caller and does not inherit its cancellation, and awaiting `.value` keeps the refresh spinner up until the fetch ends. Putting it in `load()` has two advantages over the view:
  - It can be unit-tested through the view model seam. Rows (a) and (a2) cancel the caller while the request is in flight.
  - It covers every caller at once: `.refreshable`, `.task` on reappear, and both section Retry buttons, so no call site can bring the bug back.
- **Keeping loaded content visible (orchestrator item 2).** The plan also keeps loaded sections on screen during a refresh. This removes the mid-refresh re-render that triggers the cancellation in the first place, and the shield still covers any re-render that remains, such as Today's Sessions or failed sections turning into skeletons. A section's state is assigned only when it changes, so a refresh over loaded content publishes no state change at its start.

# Phase 04 — UI Design Contract

> Visual and interaction contract for Phase 04: Booking, Payment and Discovery. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.
>
> **Scope of this contract.** Phase 04 is a bug-fix phase on a live SwiftUI app. It adds no palette, no spacing scale and no redesign. It locks (1) the design system exactly as the code has it today, inherited from `02-UI-SPEC.md` and `03-UI-SPEC.md` and not re-derived, and (2) the new or changed states, copy and interaction rules the 17 Phase 04 requirements and the 14 `04-CONTEXT.md` decisions need: one new status line and two new alert variants on Make a Booking, a locked exit rule for Request Sent, a payment card with three variants, a not-found and a load-failed state on the expert profile, paging footers on Favorites and Reviews, wired empty-state buttons, and a handful of copy and format fixes.
>
> **Every copy string in the Copywriting Contract is exact.** Where a string comes from `04-CONTEXT.md` the decision id is cited. Where it comes from Android the Android key is cited. Money in copy is shown as `CA$45.00` for illustration; any real amount comes from the shared `Money` formatter (Phase 2 D-09). Where this file has no copy for a state, the existing string in the code stays.
>
> **Live-money warning.** Every environment points at the production backend with live Stripe keys. The PAY-01 and PAY-02 states below place and release real holds. See "Real-money device session".

### 4. Exit rules for tab-owned stacks (BOOK-19, D-06; EXPL-05, D-08)

The booking flow can be started from Explore, Search, Profile (through Favorites), Bookings (Book Again) or Chats (View Profile). Phase 02 D-04 makes each tab own its stack. The **source tab** is the tab selected when the exit is tapped, because the screen is only reachable while its own tab is showing. No tab may be left holding the booking flow.

| Action | Where | Stacks reset | Tab shown after |
|--------|-------|--------------|-----------------|
| `Back to Home` | Request Sent | source tab | Explore |
| `View My Bookings` | Request Sent | source tab and Bookings | Bookings |
| `Check My Bookings` | Make a Booking alerts (section 2) | source tab (removes the form, so it cannot be resubmitted) and Bookings | Bookings |
| `Explore Experts` | Favorites empty state | Profile | Explore |
| `View My History` | Favorites empty state | Profile and Bookings | Bookings, with the **Past** segment selected |

If the source tab is Explore, "reset source tab" and the Explore reset of `Back to Home` are the same stack, reset once. The Explore stack is not reset by `Explore Experts` (only the Profile stack is). Implement as extensions of the existing `showMyBookings` / `returnToHome` shell actions plus one new action for the history case; the Bookings segment is selected through the My Bookings view model, not by pushing a route.

### 6. Expert Profile states (EXPL-01, EXPL-02, D-09, D-10)

Load states are `loading` (initial), `loaded`, `notFound` and `failed(String)`, decided only by the `GET /experts/:id/details` call. The 3-review preview call stays best-effort and silent. A 404 (branch on the status code or `ErrorCode.notFound`, never on message text) means `notFound`; every other thrown error means `failed`. This replaces the `try?` on that call.

| Property | Contract |
|----------|----------|
| `loading` | Unchanged: the seeded profile shows while the call runs, with no spinner. A seeded profile can therefore flash before a 404 replaces it (see K5) |
| `notFound` | The state view replaces the whole scroll content: `person.crop.circle.badge.xmark` icon (`.title`, light, `onSurfaceVariant`), heading, message, one accent `Back` capsule (48 pt tall, 32 pt horizontal padding, `PressScaleButtonStyle`). The system back chevron stays. The heart and the overflow menu are **removed** from the toolbar. `Back` pops one level. No Retry, because a 404 will not change |
| `failed` | Same layout with `exclamationmark.triangle` and an accent `Retry` capsule. Tapping Retry replaces the capsule with a small accent `ProgressView` while the call runs and keeps the state view on screen; on success the profile shows, on failure the state view returns with the new message. Heart and menu removed as above |
| Favorited expert that is now missing | Not removed from Favorites automatically and no Remove button is offered (D-10). The entry stays until the server stops returning it. `list_favorite_experts` already filters `moderation_status = 'active'` (migration `20261016000100`, line 601), so a 404 from a Favorites row is mostly a deleted account or a race; the `deleted_at` filter on that function was not checked here and stays a planner research item |
| Heart source | The heart reads `is_favorite` from the details response (D-09). The scan of `getClientFavorites(page: 1, limit: 100)` is removed. A missing key reads false. A profile opened from Favorites seeds the heart as filled, so it does not flicker empty then filled; any other entry seeds it empty. The server value replaces the seed when the response arrives |
| Empty sections (EXPL-02, a LIKELY item: confirm on a device before fixing) | `ExpertProfileExpertiseSection` is not rendered when there are no tags; `ExpertProfileTopicsCard` is not rendered when there are no topics; `ExpertProfileReviewsCard` is not rendered when there are no reviews. Their 28 pt (reviews 48 pt) bottom padding goes with them, so no blank gap remains. The About card and stats bar are unchanged |
| Hero rating row | Per the copy table: zero reviews reads `No reviews yet` without the star glyph or `0.0`; one review reads `(1 review)` |
| Self view | Unchanged: the heart, menu and booking buttons stay hidden for the expert's own profile |

### 7. Favorites and the full reviews list: paging (EXPL-05, EXPL-06, D-07, D-08)

Both lists use the same pattern.

| Property | Contract |
|----------|----------|
| Page size | 20 (`page` / `limit`; the server clamps `limit` to 1 to 100) |
| Next page | Fetched when one of the last 3 rows appears; never while a page is already loading |
| Stop | Stops when the loaded count reaches the server's total (or `pagination.hasMore` is false). Nothing is shown at the end |
| Footer | While loading the next page: a centered accent `ProgressView` with 16 pt vertical padding under the last row. If that fetch fails: the footer error label (`.caption`, Regular, `onSurfaceVariant`) and a `Retry` text button (`.subheadline`, Semibold, accent, 44 pt minimum hit area) in the same footer. The rows already loaded stay on screen; a failed later page never replaces the list with the first-page error view |
| Pull to refresh | Restarts at page 1 and replaces the list when it succeeds. Reviews already has `.refreshable`; Favorites gains it on the populated list |
| Duplicates | A row is appended only if its id is not already in the list, so a shifted page never shows a duplicate |
| Unfavorite | Removing a favorite removes the row locally and lowers the known total by one, so the end-of-list check stays correct |
| Empty buttons | Wired per section 4. The Favorites header tagline and the star illustration (`FavoritesGlowingStar`) are unchanged |

### 8. Search tag pills (EXPL-04)

| Property | Contract |
|----------|----------|
| Text | `lineLimit(1)` is removed; the pill text is never truncated |
| Layout | The pills (still at most 3, as on Android) sit in `TopicsSetupFlowLayout(horizontalSpacing: 6, verticalSpacing: 6)`, replacing the one-line `HStack`, so a pill that does not fit moves to the next line (Android uses a `FlowRow`) |
| Shape | A pill whose own text is wider than the row wraps its text inside the pill. The shape is `RoundedRectangle(cornerRadius: 12, style: .continuous)` with the same fill and stroke, which is visually identical to the current capsule for a one-line pill and does not distort when two lines |

<objective>
EXP-09 (Accepting a request shows the booking-confirmed screen), with D-11 (Confirmed replaces Request Decision; Back and Back to Home behave like Android 11-CONTEXT D-04/D-05), D-12 (409 `ALREADY_PROCESSED` pops to a refreshed list) and user decision U1 (1,000-unit accept message cap with a counter).

Purpose: today Accept ends on an "Accepted!" footer on a decision screen that is now stale, and `BookingConfirmedView` is never shown. An expert should land on a clear confirmation with a working Add to Calendar and a way home.

**Deliberate UI-SPEC mechanism supersession (06-RESEARCH Open Question 1).** 06-UI-SPEC section 3 says the replace uses `HomeNavigationPath.replace(with:)`. That call makes the value the only entry on the tab stack (HomeNavigationPath.swift L67-69), so Back would skip Incoming Requests, and Incoming Requests opens the decision screen with `.navigationDestination(item:)`, which is not in the path at all. This plan instead hosts `BookingConfirmedView` inside `RequestDecisionView`: the view's content switches to Confirmed in the same transaction that closes the sheet. The D-11 behavior the user locked (Confirmed replaces the decision screen; Back reaches a refreshed Incoming Requests, never a stale decision; Back to Home pops to the Dashboard) is preserved exactly, for both entry paths (list and push). UI-SPEC's "Request Decision already carries the pins" is also wrong at HEAD (0 pins), so the pins are added to `RequestDecisionView`, the screen that hosts Confirmed. 06-UI-SPEC.md itself is not edited; the SUMMARY records both supersessions.

Output: the view-model confirmation state, Confirmed hosted in the decision view, the shared failure alert with the 409 pop, the accept-message cap and counter, a `returnToDashboard` shell action backed by a new `HomeShellExit.Action.backToHomeRoot`, and tests.
</objective>

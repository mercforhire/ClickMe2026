<objective>
Gap G-06-1-summary-calendar, expert half, part 1: the decoupling (UAT 06 Test 1, checklist item 17 change request; minor). Add to Calendar exists only on the expert Booking Confirmed screen, which shows once, right after an accept. The user wants it on the Booking Summary screen too, because that screen can be reached again and again. Two causes together: Phase 6 scoped the calendar to Confirmed only, and `CalendarEventEditorSheet` takes the Confirmed display model, which only the accept path builds. This plan removes the second cause.

Purpose: let any screen present the EventKit sheet, with Booking Confirmed adding exactly the event it adds today.

Output: the sheet takes a plain `BookingCalendarPayload` (title, notes, start, end); Booking Confirmed passes its payload and adds the identical event as before. The rest of the expert half (the shared `BookingCalendarEventContent` builder and offer rule, and the status-gated button on the expert Booking Summary) is plan 06-18, split from this plan to keep each plan inside the context budget. The client half (Upcoming Booking) is plan 06-14; the Android mirror is plan 06-15. No backend change: both detail endpoints already return every field.
</objective>

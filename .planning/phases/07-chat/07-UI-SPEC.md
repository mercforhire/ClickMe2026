# Phase 07 — UI Design Contract

> Visual and interaction contract for Phase 07: Chat. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.
>
> **Scope of this contract.** Phase 07 is a bug-fix phase on a live SwiftUI app. It adds no palette, no spacing scale and no redesign. It locks (1) the design system exactly as the chat code has it today, inherited from `02-UI-SPEC.md` to `06-UI-SPEC.md`, and (2) the new or changed states, copy and interaction rules that CHAT-01 to CHAT-07 and the 18 `07-CONTEXT.md` decisions need: a pending and a failed message bubble with retry and Delete, a 10,000 character cap with a counter, a banner that replaces the composer on a blocked thread, truthful block copy, a confirm alert for Block on the Expert Profile, an unread pill on conversation rows, and the report reason picker that sends enum values. CHAT-08 is closed as not reproducible (D-17) and has no UI work. The expert chat booking-row route (D-18) has no visual change.
>
> **Every copy string in the Copywriting Contract is exact.** Executors must not paraphrase. Where a string comes from a decision, the decision id is cited; where it comes from Android, the Android key is cited; where it already ships, "shipped" is marked. Block copy describes only what the backend does (chat messaging is blocked; the other person is not notified). It makes no claim about profiles or bookings (D-05).
>
> **Non-interactive run.** No question could be asked. Every choice the CONTEXT left to discretion was made from the existing iOS code and Android parity, and is listed in "Assumptions recorded" (A1 to A14) so the user can overrule it before planning.
>
> **Live-data warning.** Every environment points at the production backend. Block, Unblock and Report change real accounts. Device checks use two test accounts (see "Device-only checks").
>
> **Cross-repo.** This contract needs no backend change and, on current evidence, no Android change (see "Android parity contract").

## Spacing Scale

Target tokens for any new or changed layout in this phase (points, multiples of 4):

| Token | Value | Usage on Phase 07 surfaces |
|-------|-------|----------------------------|
| xs | 4 | Counter gap below the composer row |
| sm | 8 | Gap between the failed "!" glyph and its bubble; pill horizontal padding; gap between the preview text and the unread pill; banner vertical padding; banner icon-to-text gap |
| md | 16 | Banner horizontal padding; banner gap between title and Unblock button |
| lg | 24 | Not used by a new Phase 07 element |
| xl | 32 | Not used by a new Phase 07 element |
| 2xl | 48 | Not used by a new Phase 07 element |
| 3xl | 64 | Not used by a new Phase 07 element |

New or changed layout, in full:

1. **Failed "!" glyph.** 20 x 20 pt, 8 pt (sm) before the bubble, vertically centred on the bubble text block (not on the status line).
2. **Failed bubble hit area.** The bubble and its status line together are one button. Minimum height 44 pt (`frame(minHeight: 44)` on the tappable group with `contentShape(Rectangle())`), because a one-line bubble is about 40 pt tall.
3. **Counter.** One `Text` line under the composer row, trailing-aligned, 4 pt (xs) below it, with 16 pt trailing padding (md) so it ends under the field's right edge. Shown only from 9,000 UTF-16 units. It reserves no space before that; the bar grows by one caption line once, when it appears (accepted, see A4).
4. **Blocked banner.** Replaces `ChattingInputBar` in the same slot. 16 pt (md) horizontal padding, 8 pt (sm) vertical padding, minimum height 56 pt (the minimum governs a text-only banner; a banner with the 44 pt Unblock capsule is 60 pt). A 1 pt top hairline `Color.white.opacity(0.06)` copies the input bar's top edge. Icon 20 pt, 8 pt (sm) before the title. The Unblock capsule is 44 pt tall (the existing card capsule is 42, left as is) with 16 pt horizontal padding inside, and 16 pt (md) from the title.
5. **Unread pill.** Minimum 24 x 24 pt (`@ScaledMetric`, so it grows with Dynamic Type), capsule, 8 pt (sm) horizontal padding, 8 pt (sm) from the preview text. It sits at the trailing end of the preview line. The time label stays at the top-trailing corner, unchanged.
6. **Profile Block in-flight overlay.** Full-screen `Color.black.opacity(0.4)` scrim with a centred `ProgressView` (`controlSize(.large)`, tint `Brand.primary`). The scrim absorbs taps. No new spacing.

Exceptions declared for new Phase 07 layout, one only: **line weights are not spacing and are not on the scale** (the 1 pt banner hairline, the 1 pt failed-bubble border, the 1.5 pt Unblock capsule stroke, which copies the existing capsule stroke). Every spacing value, padding, gap and frame size added or changed by this phase is a multiple of 4. Every new interactive control is at least 44 pt: the failed bubble group (44), the banner Unblock capsule (44), the banner row (56), the dialog and alert buttons (system).

## Typography

All text uses `Font.brand(_ style:weight:)` (rounded, Dynamic Type). Sizes are the default Content Size Category values. Line height is the system default for each style; Phase 07 sets no explicit line height and no fixed font size.

| Role | Style / size | Weight | Line height | Phase 07 usage |
|------|--------------|--------|-------------|----------------|
| Label | `.caption` / 12 pt | Regular (400); Bold (700) for the unread count | system | Composer counter `{n} / 10,000`; failed status line `Not sent. Tap to retry`; unread pill count |
| Body | `.subheadline` / 15 pt | Regular (400); Bold (700) for the banner title, the Unblock label and an unread preview | system | Banner title, Unblock capsule label, conversation preview (Regular when read, Bold when unread), failed bubble text (existing style) |
| Control | `.body` / 17 pt | Regular (400) | system | System alert titles, messages and buttons, and context-menu items, rendered by the OS |
| Display | not used | — | — | Phase 07 adds no display text |

Declared for new or changed text in this phase: **3 text sizes** (12, 15, 17) and **2 weights** (Regular 400, Bold 700). Line-height rule: system default, so body copy renders at about 1.3 to 1.4 and headings about 1.2; the contract does not override it.

Weight exceptions: none for new or changed text.

### Out of contract: pre-existing text styling

Text Phase 07 neither adds nor changes. It is existing shipped styling, recorded so a plan leaves it alone. Its sizes and weights are not contract values, so the rendered chat screens use more text sizes (for example 11, 16 and 22 pt) and the Semibold and Medium weights beyond the three sizes and two weights declared above. Listed by file reference only:

- Bubble message text (`.subheadline` Regular), sender label and the timestamp and "· Read" row (`.caption2`, 11 pt). The `Sending…` status takes the timestamp row's existing style. See `ChattingMessageBubble.swift`.

All use Dynamic Type text styles, so they scale. New multi-line copy (banner title, failed status line, block card body) carries `.fixedSize(horizontal: false, vertical: true)` so it wraps instead of truncating.

## Phase 07 UI Delta Contracts

### 1. Message bubble: pending, failed, retry, delete (CHAT-01, D-01 to D-03)

Own bubbles only. Peer bubbles are unchanged.

| State | Bubble | Status row | Interaction |
|-------|--------|------------|-------------|
| Pending (just sent, or retrying) | Normal own bubble, full fill, appears at once at the bottom | `Sending…` in place of the time, no `· Read` | Not tappable. No long-press |
| Sent | Normal | Time, then `· Read` when read (unchanged) | None |
| Failed (network error or 5xx) | Failed treatment from "Color": fill at 40%, `Brand.onSurface` text, 1 pt `Brand.error` 50% border, `!` glyph 8 pt before the bubble | `Not sent. Tap to retry`, `.caption`, `Brand.error`, replaces the time | Tap retries with the same `client_msg_id`. Long-press opens a context menu with `Delete` |

Rules:

- A pending bubble is appended and the list scrolls to the bottom in the same update (the `scrollToBottomToken` bump moves from "after a successful send" to "on append"). The composer clears at once, **stays enabled and keeps focus** so the keyboard does not drop (the current `isSending` disable and spinner are removed from the composer).
- The ack replaces the pending bubble by `client_msg_id` with the same SwiftUI identity, so there is no remove-and-insert flash; the status row cross-fades with the existing 0.2 s ease. A `message.new` echo or a page load carrying the same server id or `client_msg_id` never adds a second bubble.
- A failed bubble stays where it was appended, in list order, and later peer messages appear after it. Retry returns it to Pending; at most one retry per bubble runs at a time, repeat taps while pending are ignored.
- Delete removes the bubble locally with no request. Failed bubbles live in memory only and are gone when the thread closes or the app restarts (D-02); there is no restore.
- On `403 THREAD_BLOCKED` or `403 RECIPIENT_UNAVAILABLE` the pending bubble is removed, its text goes back into the composer and the banner (section 3) replaces the composer (D-03). Any other 4xx removes the bubble, restores the text and shows the `Couldn't send message` alert (A3).
- Motion: the only animation is the 0.2 s status cross-fade (existing). Reduce Motion needs no separate branch. No haptic.

### 2. Composer: cap and counter (CHAT-01, D-04)

- **Cap.** 10,000 UTF-16 units, the backend's `z.string().max(10000)` unit, enforced as the user types and on paste with `UTF16Prefix.prefix(_:limit:)`, never leaving half a surrogate pair. Over-long pasted text is cut silently, and the counter at the cap tells the user why.
- **Counter.** Appears at 9,000 units (Android `COUNTER_FROM`), `.caption` Regular, `ChattingBrand.onSurfaceVar`, trailing-aligned under the field row. At 10,000 the text turns `Brand.error`. Text shape: `{n} / 10,000` (section "Copywriting Contract").
- **Send at the cap.** The send button stays available at exactly 10,000. The existing rule that hides send for empty or whitespace-only text is unchanged.
- **Counter and keyboard.** The counter sits inside the input bar, so it rides above the keyboard with the bar. It is not a separate overlay.
- **Not a live region below the cap**, so typing never speaks the count (section "Accessibility").

### 3. Blocked and unavailable banner (CHAT-03, D-03, D-07, D-08)

- Replaces `ChattingInputBar` in the same slot at the bottom of the thread (and the typing strip above it is not shown). It appears for the three states in the Copywriting Contract and never for an unblocked, available thread.
- Structure: `HStack` of icon (`ChattingBrand.onSurfaceVar`, 20 pt), title (`.subheadline` Bold, `ChattingBrand.onSurface`, wraps), and, only when blocked by me, the `Unblock` capsule. Fill `ChattingBrand.navBg`, top hairline as the composer. Use `ViewThatFits` so that when the title and capsule do not fit on one line (long name, or an accessibility Dynamic Type size) the capsule moves under the title, left-aligned, at its full 44 pt height.
- `Unblock`: capsule, `.subheadline` Bold, `Brand.primary` label and 1.5 pt stroke, `PressScaleButtonStyle`, disabled with a small `ProgressView` in place of the label while the request runs, repeat taps ignored. On success the banner is replaced by the composer with a 0.2 s fade; the composer is empty, focus is not forced. On `403 NOT_BLOCKER` the banner becomes the "can't reply" state with no button and the alert in the Copywriting Contract is shown. On any other error the banner stays and the `Couldn't unblock user` alert shows the message.
- Block state is read from the thread's `GET /chats` item when the thread opens and again after a `THREAD_BLOCKED` send (CHAT-UNBLOCK §6). There is **no loading UI** for the lookup: the composer is shown while it runs, and a failed lookup keeps the normal composer (the safe default; the server still rejects a send). `blocked_by_me` missing means `false` (D-08).
- If the composer was focused when the banner replaces it, focus is dropped and the keyboard hides.
- Earlier messages stay fully readable and scrollable. Only the composer is replaced.

### 4. Thread menu (⋯)

Entries and roles are in the Copywriting Contract. The menu keeps its `confirmationDialog` form (shipped). Choosing any entry opens `Block & Report`. When the user returns from that screen after a block or an unblock, the thread already shows the new banner or composer; the screen does not reload the whole thread.

### 5. Report & Block screen (CHAT-02, CHAT-03, CHAT-04, D-05, D-07, D-08, D-09)

- The block card follows the three-row table in the Copywriting Contract. Layout, the iridescent border, paddings and capsule size are unchanged. The button is shown only when the table says so.
- `Unblock User` uses the same restorative style as the banner (accent label and stroke, A7). `Block User` keeps its existing red outline (`ReportChatBrand.errorRed`).
- The card state after each outcome follows CHAT-UNBLOCK §6: block 200 gives blocked by me; unblock 200 gives not blocked; unblock `403 NOT_BLOCKER` gives blocked, not by me, with no button; a lookup that fails keeps the card's current state.
- The reason picker lists the six enum labels and submits the selected case's raw value (D-09). A reason is still required; the existing reason error and anonymous-report copy are unchanged.
- **Details cap (D-19, added at the Step 9.5 probe, user decision 2026-11-17).** The optional details field is capped at 1,000 characters, enforced on typing and paste, matching Android and the profile `ReportUserSheet` (`maxDetailsLength = 1000`). It shows the same always-visible `{n}/1000` counter as `ReportUserSheet` (`.caption`, `ReportChatBrand` secondary text, trailing under the field). Whitespace is trimmed on submit, as in `ReportUserSheet`. The backend maximum is 2,000, so the cap prevents the 422.
- The confirm dialog and error titles are in the Copywriting Contract.

### 6. Expert Profile Block (CHAT-04, D-06)

- The `Block {name}` menu item stops opening the combined screen and opens a **centred `.alert`** (not `.confirmationDialog`: a `Menu` source makes a confirmation dialog anchor as an iPad popover, the same reasoning Phase 06 used for its Delete prompt). It is driven by one `@State` flag. No request is sent until `Block` is tapped.
- On `Block`: show the in-flight overlay (Spacing item 6), disable the menu and ignore repeat taps, call `initiateChat`, then `chatAction(threadId, "block")`. The profile stays on screen; nothing navigates to a chat.
- Success: remove the overlay and show `ToastCenter.shared.show("You blocked {name}", systemImage: "checkmark.circle.fill")`. The toast uses the existing `ToastHost` style and 4 s duration and posts a VoiceOver announcement itself. The menu keeps showing `Block {name}` (re-block is a 200 no-op). Unblocking happens in the chat.
- Failure: remove the overlay and show the `Couldn't block user` alert with the mapped message. The earlier `.sheet` that hosted `ReportChatView` from the profile is removed.
- `Report This Profile` is unchanged and still opens `ReportUserSheet`.

### 7. Conversation row: unread pill (CHAT-07, D-12 to D-14, D-15)

- When `unreadCount > 0` the row shows the pill from Spacing item 5: `Brand.primary` fill, `Brand.onPrimary` count, `.caption` Bold, `.fixedSize()` so it never truncates. At 100 or more it reads `99+`. At 0 it is not in the layout.

- Counts follow D-12, D-13 and D-16: opening a thread sets its row to 0 at once; a peer `message.new` for a thread that is not open adds 1 and moves the row to the top; the next quiet `GET /chats` reload corrects drift. Your own echoes never add. The row's visual contract is the same whichever way the number changed.
- There is **no Chats tab icon badge** (D-15) and no `Blocked` label on a row.

### 8. Expert chat booking row (D-18)

No visual change. The system-event row keeps its look, chevron behaviour and tap target. Only the destination for an expert changes (to the expert booking summary), and only if the device check reproduces the failure. If the destination cannot be resolved, the row must not push a screen that shows a load error.

### 9. Unchanged by decision

- CHAT-05 and CHAT-06: no visual change. View Profile is enabled from open, the typing strip works from open, and `Load earlier` never shows a duplicate. The button and its `Loading…` state are as shipped.
- The thread's empty, loading and error states, the typing strip copy `{name} is typing…`, the day separators and the system-event rows.
